# Pre-Production Forensic Audit — pi-dashboard

**Date:** 2026-07-26
**Commit audited:** `af4c64d` (branch `main`, clean except one untracked doc)
**Scope:** full repository — 541 tracked files, 17,304 LOC frontend, 5,207 LOC server, 5,848 LOC tests
**Method:** static import-graph reachability from both entry points (`src/index.html`, `server.js`), literal-reference sweeps for assets/classes/events/env vars, route enumeration, `npm audit`, manual read of every security-relevant route.

> **Verification boundary.** Everything marked *TRACED* was proven by following actual
> imports/references. Everything marked *NEEDS-LIVE* is a hypothesis that requires the Pi
> (CDP metrics, real hardware timings) to confirm. I did not run the Playwright suite or
> deploy during this audit — no runtime claims are made from it.
>
> **Platform note.** The brief specifies Raspberry Pi 5. `CLAUDE.md` and every deployment
> note in this repo describe a **Pi 4**. All performance findings below are written against
> the Pi 4 reality; a Pi 5 would make several of them less urgent (roughly 2–3× CPU, better
> memory bandwidth) but none of them disappear — the leaks and the fan-out are structural.

## 1. Executive Summary

This is a mature, unusually well-documented hobby-scale kiosk that has already survived
several production incidents and encoded the lessons (leak discipline, pre-push gates,
flag-gating, contract tests). The architecture is sound: a thin Express API layer over
~20 upstreams, a vanilla-JS frontend with a real event bus and a presence state machine,
and a pull-based deploy. The test suite (34 specs) and the 4-gate pre-push hook are better
than most commercial projects of this size.

**It is not, however, ready to be called production-secure**, and the reason is structural
rather than incidental: **the server has no authentication, no CORS policy, no rate
limiting, and no security headers on any route except `/admin/photos`.** On a trusted home
LAN that is a defensible choice; it is only safe *because* of the network boundary, and
nothing in the code enforces or documents that assumption. Two endpoints (`/api/tts/speak`,
`/api/ai/brief`) turn an unauthenticated LAN request into unbounded SD-card writes and
billable Anthropic spend respectively.

**Seven dependency advisories** are outstanding (4 high), all fixable with `npm audit fix`.

The dead-code surface is small but real: **8 orphaned files**, one **byte-identical
duplicate config** whose weather-icon map points at six lottie files that do not exist, a
**broken API endpoint (`/api/ai/route`) called from two live code paths**, and ~30 dead CSS
classes. None of these are breaking today — they degrade silently, which is exactly why
they have survived.

The highest-value *performance* finding is not a leak but a fan-out: **13 independent
`document.addEventListener("ha:state-updated")` handlers**, each re-invoked once per entity
on every full HA snapshot. On a house with ~200 entities that is ~2,600 handler invocations
per reconnect, on the main thread, on a Pi.

**Verdict: ship-capable on a trusted LAN after the Critical list (≈9 h). Not internet-exposable at any effort level without an auth layer (≈16 h more).**

## 6. Security Report

### CRITICAL

**S1 — Unauthenticated unbounded-cost TTS synthesis + SD-card write**
`server/routes/tts.js:92`
```js
router.post("/api/tts/speak", async (req, res) => {
  const { text, rate } = req.body ?? {};
  if (!text) { res.status(400).json({ error: "text is required" }); return; }
```
- **Risk:** No auth, no length cap, no rate limit. Every *unique* text string is synthesized
  via Kokoro and written to `server/tts-cache/<sha256>.wav`, retained 14 days.
- **Likelihood:** Medium (any LAN device — including a compromised IoT device — can reach it).
- **Impact:** High. A loop of random strings fills the Pi's SD card and burns its write
  endurance. `express.json({ limit: "256kb" })` caps one request, not the total. The prune
  job only runs every 24 h and only removes >14-day-old files.
- **Fix:** cap `text.length` (≤ 400 chars covers every legitimate caller), add a per-IP
  token bucket, and add a cache-directory size ceiling with LRU eviction. **2 h**

**S2 — Unauthenticated billable LLM endpoint**
`server/routes/ai.js:113` (`POST /api/ai/brief`), same for `/api/voice/converse`, `/api/recipe`
- **Risk:** Anyone on the LAN can drive `ANTHROPIC_API_KEY` spend at `MAX_TOKENS` 300/call.
- **Likelihood:** Medium. **Impact:** High (financial, unbounded).
- **Fix:** rate limit + a shared-secret header from the kiosk. **2 h**

### HIGH

**S3 — Zero security middleware**
`server.js` — no `helmet`, no `cors`, no rate limiter, no `trust proxy`, no CSP.
- Missing: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, HSTS, CSP.
- With no CORS policy set, Express defaults to *no* `Access-Control-Allow-Origin` header,
  which means cross-origin *reads* are blocked by the browser — but **CSRF on the state-changing
  routes is wide open**: `PUT /api/routines`, `PUT /api/delight`, `POST /api/memories`,
  `DELETE /api/memories/:id`, `POST /api/recipe`, `DELETE /api/recipe/:slug`,
  `POST /api/ha/services/:domain/:service`. A malicious page opened on any device on the LAN
  can `fetch()` these with `mode: 'no-cors'` and mutate on-device state or actuate the
  allowlisted HA services (lights, switches, scenes, scripts, media players).
- **Fix:** `helmet()`, an explicit CORS allowlist, `express-rate-limit` globally, and either
  a CSRF token or an `Origin`/`Sec-Fetch-Site` check on every mutating route. **4 h**

**S4 — Dependency advisories** — 4 high, 2 moderate, 1 low (§3). `npm audit fix` resolves
all seven without a major bump. **0.5 h + 1 h regression**

**S5 — HA proxy forwards arbitrary paths with the HA bearer token attached**
`server.js:150-176`
```js
const baseProxyOptions = { target: haTarget, changeOrigin: true, ws: true,
  on: { proxyReq: (proxyReq) => { const token = process.env.HA_TOKEN;
        if (token) proxyReq.setHeader("Authorization", `Bearer ${token}`); } } };
appInstance.use("/api/image_proxy", createProxyMiddleware(baseProxyOptions));
appInstance.use("/api/camera_proxy", createProxyMiddleware(baseProxyOptions));
```
- There is no `pathFilter` and no `pathRewrite`. Any LAN client that can construct a URL
  under these mounts gets a **token-authenticated** request into Home Assistant. `ws: true`
  additionally permits WebSocket upgrade through the same mount.
- The `SAFE_SERVICES` allowlist on `/api/ha/services` is careful and correct — and this proxy
  routes around it.
- **Fix:** add `pathFilter` restricted to the two real HA prefixes, drop `ws: true` (neither
  image nor camera proxy needs it), and confirm the forwarded path is what you expect.
  **NEEDS-LIVE** — confirm the current forwarded path with `DEBUG_HA_PROXY=1` before changing
  it, because the mount-path-stripping behaviour of http-proxy-middleware v3 under `app.use`
  determines whether today's working behaviour depends on it. **2 h**

### MEDIUM

**S6 — 47 `innerHTML` assignments, several on upstream-controlled strings**
Worst-case sites: `services/weather/renderer.js` (10), `modules/calendar.js` (9),
`modules/cameraTiles.js` (6), `static/memories/app.js` (4), `static/recipes/app.js` (3).
Calendar event titles come from external ICS feeds; Plex/Sonarr titles come from those APIs;
recipe/memory titles come from the LAN portals. `server/routes/admin.js` has a correct
`escapeHtml()` — none of the frontend does.
- **Likelihood:** Low (needs a poisoned upstream or a LAN actor). **Impact:** Medium — script
  execution inside a kiosk that holds an HA-token-proxying origin.
- **Fix:** replace `innerHTML` with `textContent` wherever the value is data, not markup.
  Mechanical, ~40 sites. **4 h**

**S7 — `/api/ha/shopping_list` POST/PATCH/DELETE unauthenticated** — mutates real HA state,
no allowlist equivalent. **Fix:** covered by S3's CSRF/origin check. **0 h incremental**

**S8 — Admin upload overwrites silently** — `admin.js` `filename` callback derives the name
from `originalname`; a second upload of the same name replaces the first with no warning.
Auth-gated, so low reach. **Fix:** suffix on collision. **0.5 h**

**S9 — `/env.js` leaks internal topology to the browser** — `HA_HOST`, `GO2RTC_HOST`,
`HOME_BASE` (a home address), and BOM entity IDs are served to any LAN client. No credentials
leak (`HA_TOKEN` correctly stays server-side). Acceptable on a trusted LAN; a hard blocker
for any exposure. **Fix:** gate behind the same auth as S3. **1 h**

### LOW

**S10** — `console.log` of every HA API call (`server.js:73`, `[ha-api]` logger) includes
`req.originalUrl`, which carries entity IDs. Verbose, not sensitive. **0.5 h**
**S11** — No log rotation configured for the `dashboard.service` journal. **0.5 h**
**S12** — `server/.env.example` and root `.env.example` both exist; the dual-path dotenv
fallback in `server.js:57` means a stale `server/.env` can silently shadow intent. **0.5 h**

### Verified clean (no action)

- No `eval()`, no `new Function()`, no `child_process` anywhere in server or frontend code.
  The only `child_process` uses are in `scripts/verify/*` and `scripts/fault-injection.mjs`
  (developer tooling, not shipped).
- **`server/routes/admin.js` is genuinely well-built**: HTTP Basic + `crypto.timingSafeEqual`,
  magic-byte content validation (not just extension), `path.basename` + prefix re-check in
  `safePath()`, 25 MB limit, `escapeHtml()` on all rendered names. This is the security
  standard the rest of the server should be held to.
- Path traversal: no route builds a filesystem path from unsanitized user input. `memories.js`
  confines writes to a single `authored.json`; `routines.js`/`delight.js` write one fixed file
  each; `recipe.js` slugifies.
- HA service invocation is allowlisted to 12 safe services (`ha/haRoutes.js:6`).
- No secrets in tracked files. `.env` correctly gitignored.

## 9. Raspberry Pi Performance Report

### Ranked by expected gain

**P1 — HA state fan-out (HIGHEST GAIN)**
`services/homeAssistant/events.js:107-117`
```js
on("ha:states", (entities) => {
  entities.forEach((entity) => {
    updateEntity(entity);
    document.dispatchEvent(new CustomEvent("ha:state-updated", { detail: entity }));
  });
```
There are **13 `document.addEventListener("ha:state-updated")` handlers**
(motionTrigger, presence, routineRuntime, arrivalGreeting, cameraPopupOverlay, cameraTiles,
doorbellAlert, mediaPanels, mediaStatus, systemStatus, todo, weather/renderer, + 1).
Every full snapshot dispatches **one event per entity**, and each is delivered to all 13.
At ~200 HA entities that is **~2,600 synchronous handler invocations on the main thread**,
per snapshot — and `haWs.js` re-sends a full snapshot on every reconnect. Most handlers
begin with an entity-ID filter and immediately return, so the work is almost entirely
dispatch overhead, but it is unavoidable dispatch overhead on the UI thread.
- **Fix:** batch the snapshot into one `ha:states-updated` event carrying the array, and let
  each consumer filter once. Keep the per-entity event for incremental `state_changed`
  (where fan-out is 1×13, which is fine).
- **Expected gain:** near-elimination of reconnect-time UI stalls. **3 h**
- *NEEDS-LIVE*: measure with `/kiosk-metrics` before/after.

**P2 — `eventBus` has no error isolation**
`core/eventBus.js:12` — `listeners[event].forEach(handler => handler(payload))`.
One throwing handler silently kills every subsequent handler for that event *for the life of
the page*. On a display that runs for weeks, this is a slow-degradation trap: the dashboard
half-works and nothing in the logs says why.
- **Fix:** wrap each call in try/catch and `console.error` the failure. **1 h** — best
  effort-to-value ratio in this entire report.

**P3 — `eventBus` has no `off()`**
37 `on()` calls sit inside `init*()` functions. Today every one of those inits is called once
from `core/app.js`, so nothing leaks. But the API makes leak-free code *unenforceable*: the
moment any per-event path (a popup, a view re-init, a recovery re-arm) calls an `init` twice,
handlers accumulate with no way to remove them. Given this repo's documented history
(709 zombie lottie wrappers, 230k detached nodes), this is a loaded footgun.
- **Fix:** add `off(event, handler)` and return an unsubscribe function from `on()`. **1.5 h**

**P4 — 41 uncoordinated `setInterval`s in the frontend**
Across 26 modules, all registered at init (correct per CLAUDE.md's discipline — no per-event
timers). But they are uncoordinated: each fires on its own phase, so the Pi never gets a long
idle window, and `screensaver.js` alone runs 6.
- The screensaver *does* correctly `clearInterval` all four of its timers in `exit()`
  (`clockTimer`, `infoTimer`, `photoTimer`, `driftTimer`) and `clearTimeout(tenderTimer)`.
  That teardown is symmetric and correct. ✅
- **Fix:** a single coordinated scheduler (one 1 s tick driving a priority queue) would let
  the CPU idle between batches. Meaningful on a Pi 4, less so on a Pi 5. **6 h, medium gain**

**P5 — 47 `addEventListener` calls, 1 `removeEventListener`**
Concentrated in `cameraTiles.js` (6/0), `cameraPopupOverlay.js` (6/0), `mediaStatus.js` (5/0),
`homeAssistant/client.js` (4/0), `systemStatus.js` (4/0). Same analysis as P3: all currently
at init, so no leak today, but no teardown path exists if any of these ever become per-event.
`cameraPopupOverlay.js` is the one to watch — popups are inherently per-event.
- **Fix:** audit `cameraPopupOverlay.js` specifically for symmetric teardown. **2 h**

**P6 — 20 `requestAnimationFrame` sites across 11 files**
`services/atmoFx/runtime.js` and `weatherMotion.js` run genuine render loops. CLAUDE.md
already records the root cause: *any* running animation forces a 60 fps whole-page composite
costing ~1 GPU core on the Pi. The mitigation is in place and correct — `freezeLotties()` on
screensaver enter, `.screensaver-active` CSS killing marquee/aurora/stars.
- **Open question:** does `atmoFx/runtime.js` fully stop its rAF loop under
  `screensaver:changed`? It subscribes at line 614, but I could not confirm from static
  reading that the loop is cancelled rather than merely no-op'd. *NEEDS-LIVE* — one
  `/kiosk-metrics` GPU sample in Mode 0 settles it. **1 h to verify**

**P7 — Bundle size**
`dist/assets/index-*.js` = **425 KB**, `index-*.css` = **96 KB**, `index.html` = 30 KB
(327 elements). For a single-page kiosk that loads once and runs for weeks, this is fine —
parse cost is paid once. **No action.** Do *not* code-split; it would add complexity for zero
benefit on this access pattern.

**P8 — Synchronous filesystem access on the server**
`server/routes/tts.js` uses `existsSync`, `readFileSync`, `writeFileSync`, `readdirSync`,
`statSync`, `unlinkSync` — all synchronous, on the request path, against SD-card storage.
Every `/api/tts/speak` blocks the event loop on a cache read; `pruneCache()` blocks it on a
full directory `stat` sweep. On SD-card I/O this is measurably worse than on SSD.
- **Fix:** convert to `fs/promises` (the rest of the server already uses it). **1.5 h**

**P9 — 33 `console.log`/`debug`/`info` calls ship to production**
25 frontend, 8 server, plus the per-request `[ha-api]` logger. On a kiosk that never reloads,
Chromium retains console history — a slow memory drip, and it makes the real errors
unfindable. **Fix:** a leveled logger gated on `HA_DEBUG`/`NODE_ENV`. **2 h**

## 14. Screensaver & Motion System Audit

**Lifecycle (TRACED)**
```
init: initScreensaver(flags) → build() → register __hooks → loadPhotos() [async]
      syncNight() every 60s ─┬─ !active && night  → engageScreensaver()
                             ├─ active && boundary crossed → applyNight()/exit()
                             └─ day rolled over  → loadPhotos()      (guarded by loadedDay)
idle: resetIdleTimer() → setTimeout(enter, isNight() ? NIGHT_IDLE_MS : IDLE_MS)
enter():  active=true → applyNight/Atmosphere → tender-memory lane OR slideshow
          → freezeLotties() → 4 setIntervals → emit("screensaver:changed", true)
exit():   emit(false) FIRST → clear 4 intervals + tenderTimer → unfreezeLotties()
          → switchView("home") → resetIdleTimer()
wake:  motion (kitchen only) | any HA state change reaching motionTrigger
```

**Correct**
- ✅ Teardown is symmetric — all four intervals and the tender timeout are cleared in `exit()`
  and nulled.
- ✅ `enter()` and `exit()` both guard on `active`, so double-entry/double-exit are safe.
- ✅ `freezeLotties()`/`unfreezeLotties()` are paired.
- ✅ `emit("screensaver:changed", false)` fires *before* teardown in `exit()`, so the presence
  FSM sees the transition even if teardown throws. Deliberate and correct.
- ✅ Night idle uses a shorter timeout — good ambient behaviour.

**Issues**

| # | Severity | Issue |
|---|---|---|
| SS1 | ~~MED~~ **STRUCK — FALSE POSITIVE (2026-07-30)** | ~~`loadPhotos()` in `syncNight()` is fire-and-forget with no in-flight guard. A slow Immich fetch spanning the 60 s tick can start a second concurrent load.~~ **A second load cannot start.** `loadPhotos()` assigns `loadedDay` as its first *synchronous* statement (`screensaver.js:233`), and an async body runs synchronously to its first `await` — so `loadedDay` is already today when line 611 receives the promise, and the next tick's `toDateString() !== loadedDay` is false however slow the fetch is. **The day check IS the in-flight guard.** The only other repeating caller, `setInterval(loadPhotos, 6h)` (`:841`), is gated `immichEnabled && !dailyMemoriesEnabled` — mutually exclusive with :611's `dailyMemoriesEnabled`, so the two can never both be armed. Init's `await loadPhotos()` (`:820`) precedes `syncNight()` (`:833`) and both timers, disarming the day-roll branch at boot. Both properties are now pinned by `tests/photo-reload.spec.js` (each verified failing against its own regression). |
| SS2 | MED | Only kitchen sensors wake the display (§13). Five cameras' motion is invisible to the wake path. |
| SS3 | LOW | `motionTrigger` calls `resetIdleTimer()` then `wakeScreensaver()` → `exit()` → `resetIdleTimer()`. Redundant first call; harmless but fragile. |

## 16. Recommended Production Logging Strategy

Currently 33 `console.*` calls ship, plus a per-request `[ha-api]` logger, with no levels,
no rotation, and no correlation.

```
LEVEL   USE                                          SINK
error   upstream failure after retries,              journald (always)
        uncaught page errors, HA disconnect
warn    fallback engaged (Claude→Ollama,             journald (always)
        PC Kokoro→NAS), recovery re-arm
info    lifecycle: boot, deploy, service start,      journald (always)
        screensaver enter/exit
debug   per-request tracing, entity updates          gated on HA_DEBUG=1
```

- Gate on `NODE_ENV` + `HA_DEBUG` (both already exist as env vars).
- Move the `[ha-api]` per-request logger to `debug`.
- **Frontend:** the kiosk never reloads, so console history accumulates. Route frontend errors
  to a `POST /api/log` bounded ring buffer surfaced on `/api/system/health`, and keep the
  browser console clean.
- Add `journald` rate limiting + rotation in the systemd unit — currently unbounded on the SD card.
- `healthService.js` already maintains a freshness registry; it is the natural home for the
  error ring buffer.

**Effort: 3 h.**

## 17. What This Audit Did Not Cover

Stated plainly so the gaps are not mistaken for clean bills of health:

- **No live Pi measurement.** Every performance claim marked *NEEDS-LIVE* (P1, P6, blob
  revocation, S5's proxy path behaviour) needs `/kiosk-metrics` or a CDP session to confirm.
- **The test suite was not run.** 34 specs exist; the pre-push hook runs them; I did not.
- **Home Assistant entity existence is unverified** — 60+ IDs are consistent but unproven
  without a live HA connection.
- **`tools/voice-pc/` and `tools/voice-agent/` (Python)** were inventoried but not audited
  line-by-line; they run on the PC and Pi respectively, outside the Node application.
- **`.reference/` (265 MB, 445 files)** was deliberately excluded as a known-dead untracked
  mirror, not analysed.

## 18. Closing Judgement

The engineering discipline in this repository is genuinely above average — the incident
post-mortems encoded in `CLAUDE.md`, the flag-reversibility verifier, the contract-test
philosophy, and the pre-push hook's honest reasoning about its own gates are all things
most production teams do not have.

The gap is that **the security model is entirely implicit**. Every unauthenticated endpoint
is safe only because of a network boundary that no code asserts, no config documents, and no
test protects. That is a fine posture for a home LAN and an unacceptable one for anything
called production. The Critical list closes the cost-unbounded holes; the High list closes
the CSRF surface and the one genuinely broken feature.

Nothing here is architectural rework. **≈26 hours of focused work makes this repository
defensibly production-ready for its actual deployment target.**
